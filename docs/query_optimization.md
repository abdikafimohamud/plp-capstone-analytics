## Test setup

- **Database:** PostgreSQL 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1) on x86_64-pc-linux-gnu, `shared_buffers=128MB`, `work_mem=4MB`, JIT off
- **Data:** 10,338,607 events, 100,000 end users, 10 tenants (tenant 1 is the largest, ~25% of all rows), 90 days, monthly partitions
- **Method:** `EXPLAIN (ANALYZE, BUFFERS)`; 1 warm-up run, then 5 timed runs; the **median** `Execution Time` is reported (warm cache)
- **Before** = schema at migration V5 (primary keys, FK indexes, BRIN on `occurred_at`). **After** = V7 (V6 adds the optimisations below)

### 3. CHANGE
**Index** (V6): `CREATE INDEX events_tenant_type_time_cov ON events (tenant_id, event_type_id, occurred_at) INCLUDE (user_id)`.

The funnel only needs 4 of the 8 event types, but ~95% of a tenant's events are engagement events (page_view, feature_used, ...). Before, PostgreSQL had to read every event of the tenant in the window and throw most of them away. The covering index is ordered by event type, so the planner reads *only* the funnel events, and `INCLUDE (user_id)` makes it an index-only scan (no table access). The SQL text is unchanged.

### 3. CHANGE
**Pre-aggregation + query rewrite** (V6): table `agg_user_activity(tenant_id, user_id, first_event_at, last_event_at)`, maintained incrementally by `refresh_rollups()`.

"Active on or after day N" is exactly `last_event_at >= signup_at + N days`, so the retention query never needs the raw events: it joins `end_users` to one row per user instead of scanning every event of the tenant. The result is identical (verified row-by-row), and because the rollup keeps `min/max` per user it survives dropping old raw partitions.

## Experiments

### E1 - Does the BRIN index earn its keep?
Cross-tenant scan of the last 6 hours (what the rollup refresh and operator dashboards do). `DROP INDEX` is run inside a transaction and rolled back, so the comparison is on identical data.

| | Median | Scan |
|---|---:|---|
| without BRIN | 175.0 ms | Seq Scan |
| with BRIN (`events_occurred_at_brin`) | 48.5 ms | Bitmap Heap Scan + Index Scan + Bitmap Index Scan |

**3.6x faster.** The primary key starts with `tenant_id`, so it cannot serve a time-only filter; BRIN can because events are inserted in time order, and it costs a few hundred KB instead of a multi-hundred-MB B-tree. Plans: `docs/benchmarks/e1_brin_with.txt`, `e1_brin_without.txt`.

### E2 - What does Row-Level Security cost?
Q1 run as the table owner (bypasses RLS) versus as the real `dashboard_svc` login with `app.tenant_id = 1` (RLS policies applied).

| | Median |
|---|---:|
| owner (no RLS) | 46.7 ms |
| dashboard_svc (RLS on) | 36.5 ms |

Ratio: **0.78x**. The policy `tenant_id = current_tenant_id()` is a STABLE function, so the planner evaluates it once and still uses the index.
